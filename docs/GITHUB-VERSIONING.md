
## 回退触发条件

1. 必须通过的测试或构建失败，或申请、排队、续期、提醒、回收出现功能退化。
2. 出现错误目标、重复邀请/回收、回执丢失，或外部操作结果不明。
3. 当前身份、角色、容量或桌面隔离检查异常，无法满足启用条件。

登录失效或官方强制验证应停止外部操作并恢复合法会话，不能靠回退代码绕过验证。只有确认新版本代码导致问题、且旧版本与现有数据库兼容时，才恢复旧代码。

## 运行环境回退步骤

1. 在**当前实际运行项目**中执行 `node scripts/agentless/stop.mjs` 请求优雅停机。等当前办理与回执结束、确认退出，再停用对应计划任务，避免重新启动。停止超时保留日志、锁和租约；不强杀后删记录。
2. 保留当前代码版本、运行配置、数据库备份、日志和计划任务定义。这些备份留在受保护的本机位置，不能提交到公开仓库。先核对未完成租约与官方成员/邀请，明确不确定操作的实际结果。
3. 按上节在新目录恢复并验证 `agentless-v5`。全新克隆不会包含生产 Cookie、数据库或已启用配置。不要直接运行第二份执行器。
4. 将已验证版本作为唯一运行代码恢复到受控运行目录；保留实际生产运行数据及必要的登录档案。文件替换和后续版本新增文件清理应以两个 Git 版本的差异为准，不递归删除整个生产目录。
5. 若网页版本也需回退，在 Sites 管理能力中选择第 5 版部署或重新发布该版本源码，保持访问控制不变。版本 ID：`appgprj_6adace8f4e7481919901f886e4a0a2f2~appgver_bae20150e5bc8191b37a9a525801f863`；原成功部署：`appgdep_6adb086aa21481918c5e4517228c183b`。本仓库推送不会自动完成 Sites 回退。
6. 数据库不能仅因源码回退而恢复旧备份。先检查迁移兼容性；备份恢复可能丢失新申请、续期及操作回执，须先整理差异并完成状态对账。
7. 用恢复版本只读核对管理员、完整成员与邀请、4 个已购席位、受保护角色及门户状态。确认没有未完成外部操作、冲突租约或第二个执行器，再启用唯一实例。
