# TRAE 版对照与优化结果

## 结论

`business-seat-portal-trae` 从原版相同基线 `aa2742d` 派生。应用层的员工申请、队列和计费状态、席位到期处理、页面及认证逻辑均随原版拷贝保留；本次差异并不是重写门户，而是在副本中增加 TRAE 的确定性巡检与回执通路。TRAE 方案能让**定期巡检**不调用 Codex 模型，但**实际管理员页面操作**仍需 TRAE 代理执行，不能据此承诺所有环节零模型或无人值守。

## 原版核心功能

| 领域 | 原版行为 | TRAE 副本状态 |
| --- | --- | --- |
| 登录和数据隔离 | ChatGPT 登录、管理员/员工识别；员工白名单独立于工作空间席位；员工只读写本人记录 | 保留相同门户和服务端实现 |
| 申请和排队 | 按小时申请，FIFO；校验容量、避免重复申请；排队、取消及等待估算 | 状态机和 UI 与原版相同 |
| 租期管理 | 使用中续期、限制单次时长、提前申请释放；服务端 tick 更新倒计时和到期状态 | 状态机和 UI 与原版相同 |
| 席位生命周期 | 邀请待接受、加入核对、五分钟邀请窗口；到期前 30 分钟通知；逾期撤回；到期/提前释放后回收 | 业务规则保留；执行方式须由 TRAE 适配器与外部前置条件补齐 |
| 官方成员核实 | 以目标 Workspace 的完整官方成员/邀请清单为证据；仅普通成员可自动处理；Owner、管理员、容量异常保护 | skill 规定相同核对步骤；TRAE 浏览器登录和 Cloudflare 通行尚未验收 |
| 独占和故障 | claim/complete 租约、防重复操作；明确的局部隔离与全局暂停；按 FIFO 继续未受影响任务 | 复用原来的计划与回执 API；本次修正隔离项不再循环唤醒 |
| 界面体验 | 员工端申请、队列、倒计时、续期及管理员状态页面 | 页面、样式与交互组件未改；本地源码继承原版 |

## 原 TRAE 适配差距

1. **触发通路不同。** 原版检查器可以把有效事项送入当前 Codex 对话；TRAE 没有等价的事件推送端点。适配器只能写入 `pending.json` 并退出码 3，必须另有 TRAE 任务或操作者读取它。没有可验证的按事件唤醒接口，因此不能宣称自动接单已经等价。
2. **邮件通路不同。** 原版可使用已连接 Gmail 的本机直发；TRAE 适配器不持有 Gmail 连接器，只接受云端 HTTPS `relay`。此副本未配置或验收 relay 时，提醒邮件尚不能确认可用。
3. **操作浏览器不同。** 门户回执客户端使用独立 Edge 登录档案；官方成员列表由 TRAE 的浏览器操作。两会话不同，且 TRAE 是否能通过 `admin.openai.com` 的安全检查仍需实测。
4. **旧执行方并行风险。** 原适配器在正常巡检前没有验证旧按需 Windows 任务是否已禁用。
5. **隔离项循环。** 原适配器遵循共享队列的事件指纹，但在 `blockedOperations` 仍存在时会再次派发同一被隔离员工。
6. **状态可读性。** 原适配器对全局异常和已有租约分别报告为空闲，容易把“暂停/等待”误看成无事可做。
7. **本机状态保护。** `.runtime-trae/` 本地 D1 状态目录原先未列入 ignore 规则。

## 本次落地改动

- 增加 TRAE 专用检查器、门户客户端、回执命令、Edge 登录引导、TRAE skill 和运行手册；巡检器复用原版计划接口与故障/租约模型，不调用 `codex.exe` 或模型 API。
- 每轮真实巡检前由 `legacy-guard.mjs` 核验根目录旧 Windows 任务为 `Disabled`，且原版项目 `.sites-runtime/queue-checker/status.json` 三分钟以上未更新；本机还必须显式确认 `legacyCheckerDisabled:true`。默认配置为关闭。此检查只读原版状态文件，不写原版目录。
- 按云端 `blockedOperations` 的邮箱和目标 ID 过滤被隔离员工的邀请、回收和加入核对；无关员工可继续处理。管理员解除隔离后事件才重新出现。
- 全局错误显示为 `blocked`，有活动租约时显示 `waiting`；避免把故障或并发操作显示成 `idle`。
- 将 `.runtime-trae/` 加入副本 `.gitignore`，避免本地数据库进入版本管理。
- 在副本 `AUTOMATION.md` 标明业务规则共用、Codex 运行步骤仅为原版参考，TRAE 运行以 TRAE 专用文档为准。
- 保留原网页代码、UI、状态机与旧脚本；没有对原项目目录写入。本次没有部署 Sites、配置 relay、启用计划任务或执行真实成员操作。

验证结果：全量 Node 测试 **140 项通过**；副本应用构建通过；新增 TRAE 执行器和测试文件的 ESLint 检查通过；`git diff --check` 通过。由于没有触碰线上资源，这些是代码级验证，不代表管理员后台、邮件 relay 或真实席位操作已验收。

## 推荐部署路径

1. 保持员工门户和数据库为唯一业务状态源；不要同时启用原版 Codex 检查器与 TRAE 检查器。
2. 在 TRAE 版副本部署/确认 `/api/codex` 和 `/api/portal` 的管理员权限保护，确认目标工作空间、Owner 和已购席位快照正确。当前本地源码中服务端标记已支持 `local:trae-cn:`；未部署前，现有线上站点不会自动获得该显示行为。
3. 设置并真实验收云端 HTTPS 邮件 relay（固定提醒模板、唯一通知号、精确截止时间和门户续期链接、真实 message ID）；不可与 Gmail Connector 同时发送。
4. 先禁用旧 Windows 任务和 Codex heartbeat，确认旧任务状态以及 3 分钟静默，再用本人登录分别建立门户回执 Edge 档案和 TRAE 官方后台浏览器会话。
5. 先运行 `checker.mjs --dry-run`，再启动普通 Node 定时巡检；仅检查程序按分钟运行，不调用模型。检测到新 `pending.json` 后由 TRAE 处理：官方全量观察 → claim → 单项操作 → 复核 → complete → ack。
6. 在独立测试成员上验收申请、FIFO、续期、提前释放、30 分钟邮件、五分钟接受/撤回边界、真实邀请、真实移除及容量归还后，再允许正式切换。

## 尚未验收、不能宣称完整自动化的边界

- 本机尚无经过证实的 TRAE 事件推送接口；若靠 TRAE 模型定时轮询，就会产生相应模型调用。当前代码只保证 Node 巡检本身 `modelCallsByChecker:0`。
- HTTPS 邮件 relay、TRAE 官方后台登录、Cloudflare 通行和实际管理员审批均未在本次运行中验证。
- 管理员 UI 可能要求即时审批；系统拒绝时适配器只能按 `approval_required` 隔离，不会绕过审批。
- TRAE 副本保留旧 UI 和业务逻辑，但线上员工仍访问已经部署的 Site。修改本地副本不会改变线上站点；要使 `local:trae-cn:` 状态指示等新服务端改动生效，须单独构建并部署该副本。
