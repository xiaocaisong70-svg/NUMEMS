# V12 历史归档、申请限流与数据回退

本改动不删除业务历史。它解决的是每次申请、刷新和调度都复制/重写全部历史的增长问题：当前分配状态保持较小，较早记录移到同一 D1 数据库的索引归档表。

## 热状态与持久归档

- `portal_state` 保留全部进行中的申请、最近 150 条已结束申请、最近 500 条通知、最近 500 条审计。
- 当前未结案租约、隔离任务、故障来源所需申请始终保留；相关邮件租约的通知和当前使用周期的通知去重键始终保留。最新工作空间故障及未结案目标的关联审计始终保留；无关旧审计照常归档。
- 长期不断续期的申请不会锁住所有旧通知：过去使用周期的通知可以归档，当前周期与邮件办理中的通知仍保留。
- 规则引擎、成员桥接与空闲核对不再提前截断审计；完整组合转换结束后统一原子归档，即使一次批量转换产生超过 1000 条事件也不丢失。
- `portal_history` 以 `(kind,id)` 为主键，保存原始记录；`kind` 区分申请、通知、审计，另有所有者和时间索引。
- 归档插入与热状态 CAS 更新处于同一个 D1 `batch()` 事务。任何插入失败都会回滚更新；旧 revision 的整个事务既不插入归档，也不覆盖并发申请。
- 不归档当前租约、隔离项、官方快照或既有有界操作回执；归档不等于实际成员回收，也不会释放容量。

`/api/history` 使用服务器身份及最新员工白名单授权，并在读取后再次检查权限。员工只能读取其本人邮箱及身份标识的记录；审计仅管理员可读。游标采用固定排序键分页，默认每页 50 条、最多 100 条。页面的“查看更早记录／加载更多历史”按需读取，不把冷历史重新放回席位分配数据。

完整持久历史仍会随业务累计，占用 D1 存储；它不会再无限扩大每次读写的热 JSON。管理员显式打开历史分页时才计算归档数量，达到 50,000 条会提示评估额度、离线导出或制定保留期限。系统不静默删除历史，也不在每次轮询执行全表计数。若需要固定总存储上限，应另行明确历史保留/导出/删除策略。

## 申请与续期限流

- 每个非管理员员工：成功申请每 UTC 自然小时最多 12 次，每 UTC 自然日最多 60 次；成功续期每 UTC 自然小时最多 12 次。
- 使用服务器时间，不依赖浏览器时钟。小时或日窗口切换后相应计数恢复。
- 失败操作不消耗预算；相同 `requestKey` 的重复请求不消耗预算。
- 申请取消、提前释放、有效到期回收和官方对账不受这些申请/续期预算阻拦。
- 限流与操作在同一次 CAS 写入。计数仅保留当前 UTC 日期内、仍在白名单中的员工，不积累无限事件数组。
- 原申请已归档后，原 `requestKey` 的重试仍返回幂等结果；每一次 CAS 重试都重新查询归档，避免并发归档造成重复申请。
- HTTP 限流返回 429；不会撤销现有席位或重新排序已存在的队列。

## 回退 V11 的数据准备

迁移 `drizzle/0001_chilly_squirrel_girl.sql` 仅新增表和索引。V11 可在存在该表时运行；禁止删除该表或反向执行破坏性 SQL。

回退前停止执行器、停用云端分配与成员办理，确认当前租约、隔离项、故障来源全部结案。还必须先结清 V12 的 `whitelist_revoked` 待撤邀申请：V11 不认识此原因，不能直接交给旧版按普通成员回收处理。

调用维护能力时，必须提交最新数据库 revision。`lib/history-rollback.ts` 中的 `restoreV11History` 会：

1. 读取 **当前** 热状态和归档，而非使用发布前快照覆盖新业务。
2. 核实调度和执行已停用、没有未结案证据、没有 V12 特有待撤邀操作。
3. 按记录 ID 合并，优先保留当前热记录；保留新申请、真实成员回执与归档表。
4. 使用数据库 revision CAS 写入，若并发状态变化则拒绝写入并要求重新核对。
5. 重建后单文档超过 1.5 MB 时先拒绝，保持原数据不变；不得宣称旧 V11 能承载任意大的完整历史。此时应保留归档兼容读取能力，或先经管理员确定离线归档方案。

成功后再部署已保存的 V11 源码/部署包和匹配执行器。验证当前业务申请、容量、官方名单与回执一致，历史数量等于热记录和归档的去重并集。归档表继续保留，不能因为恢复完成而删除。

## 验证

`tests/history-storage.test.mjs` 使用真实 SQLite 及事务化 D1 适配器验证归档完整性、CAS 冲突、事务失败回滚、员工隔离、游标分页、旧幂等键并发归档、长租期旧通知清理、限流和当前数据回退。远端真实 D1 验收使用独立虚构数据环境，不修改生产员工申请。
