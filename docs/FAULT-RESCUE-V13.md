# V13：普通程序优先、故障时单次 Codex 后备

## 运行边界

申请、排队、续期、网页提醒、邀请、加入核对、撤邀和回收仍由原有确定性规则及普通执行器完成。正常轮询不启动 App Server，也不调用模型。只有正式执行器经过有限自动恢复仍失败，并保存 `faultRescueEligible: true` 后，故障后备才可能运行。

目前后备范围为 `read_only_reconcile`：诊断官方页面、读取指定运行记录、核对原操作回执，必要时调用已受保护的 `admin status`、`recover-browser`、`reconcile`。它不能发送新的邀请、撤邀或移除成员，不能改变截止时间、白名单、权限、席位数量或源码。角色、容量和工作空间错误只保持暂停并在网页说明，不自动交接给模型。

模型后备不能保证解决官方真人验证。普通 `challenge`、加载中或网络不通只表示尚未恢复，不足以要求管理员认证。只有指定官方工作空间页面的新鲜 `interaction_required` 或 `login` 证据，才能形成“需要本人操作”的结果；不点击或代解验证码、不复制 Cookie、不改浏览器伪装参数、不自动填写凭据。

## 两阶段交接

1. 日常执行器完成 `finally` 关闭浏览器、释放锁；监督程序核对 PID 已结束、无残留锁、桌面隔离审计没有窗口落入用户输入桌面，并尊重停机请求。
2. 短暂启动隔离管理员元数据会话，执行 `prepare-fault-rescue`。本机先写入准备意图，再以当前故障 ID 调用 `begin_fault_rescue`。服务器保存独占处置凭证并禁止新的成员和邮件 claim。凭证仅留在受保护运行目录。
3. 管理员会话退出且再次通过进程和窗口审计后，普通程序才通过 App Server 的 `thread/queue/add` 向既有授权聊天发送一次简短故障消息。固定客户端 UUID 及不可重复创建的磁盘意图文件在发送前保存；发送响应丢失也不会盲目重发。
4. 后备通过 `fault-rescue-ack.mjs` 写入结束请求，然后结束模型轮次。ACK 文件不证明模型已结束，更不证明业务恢复。
5. 监督程序先用 `thread/read(includeTurns:false)` 验证聊天身份，再用官方 `thread/turns/list` 的 summary 分页查询，默认每页 8 条、最多 25 页，仅保留用户消息 ID、客户端 ID、轮次和根轮次元数据。它不完整加载长聊天，也不复制工具正文；原来的 20 MB 协议缓冲保护保持不变。用服务端 `userMessage.clientId` 精确绑定本次消息及其根轮次，关联链中每个轮次均实际进入 completed、interrupted 或 failed 后，才允许启动隔离的 `finish-fault-rescue`。分页预算内缺少目标或根链时保持未确认，不以队列消失代替结束证明。
6. finish 会再次独立核对轮次、读取官方完整名单，并按原租约核对不明操作。模型声称恢复但普通执行通道未通过核对时，按 unresolved 结案；普通程序已独立证明健康时，即使模型未写 ACK 或认为 unresolved，也可按真实证据 recovered。只有匹配原故障类型的新鲜官方交互/登录证据才可 needs_human，不能把 unknown 原操作转换成人工认证问题。是否 recovered 最终受服务器新鲜官方观察、无租约、无隔离和无全局故障等条件约束。
7. 只有 finished/recovered、确切结束证明、云端结案、原日志 settled、管理员成功报告、健康状态和无可见窗口审计全部一致，才生成带四份原始字节摘要的启动票据。原生宿主在互斥锁内重新核验后才能恢复日常执行器。

## 去重、超时和不明结果

- 同一连续故障最多一次模型唤醒。进程重启、故障 ID 改变或普通后台检查时间刷新均不能单独重置；必须有真正通过完整核对的健康周期，或已确认 recovered 的前一轮。
- 本机意图、客户端 UUID、云端故障票据和原操作日志都属于可靠性证据，不能通过删除运行目录“解除阻塞”。恢复备份时也必须一起保留。若运行目录丢失但云端仍有 pending/uncertain 票据，应停止并核对，不能重新创建一轮消息。
- 队列中找不到消息不表示发送失败或模型已停止；只读查询仍无精确证据时保持独占，不释放执行权，也不重发。
- 模型执行预算默认从实际开始时间算五分钟，不包含排队时间。到期只可中断完全属于本消息的独占轮次，并且只请求一次；summary 不能证明轮次没有其它用户消息，所以当前分页通道不会仅凭 summary 发起中断。消息进入已有用户轮次、根轮次不明或缺少完整独占证据时，保持暂停，禁止误中断当前开发或用户轮次。中断响应也不是结束证明，必须再看到服务端终态。
- finish 响应不明时读取云端处置状态恢复回执，不把请求返回异常解释为“没有成功”。uncertain 票据继续阻止新 claim。
- 模型已结束但仍 unresolved 的浏览器故障，不再唤醒模型。原日志已 settled 时，普通程序按 1、2、5、10、15、30 分钟持久退避尝试只读 `recover-browser`；官方完整核对成功后，再通过现有隔离 probe 和启动守卫恢复。登录、权限、容量或原操作不明不会进入该自动重试路径。
- 已确认发生在 claim 之前的精确 `page.evaluate: Target page, context or browser has been closed` 错误，有独立的普通程序恢复分支：要求明确的 `localContextRecoveryEligible` 标记、原日志 settled、无活跃处置票据及完整进程/隔离/停机守卫。它先保存 `local-context-retry.json`，按同样的持久退避执行 `recover-browser`；只有新鲜官方快照与匹配云端健康检查通过，才运行隔离 probe。该分支不唤醒模型，也不把新的云端 unknown、权限或容量故障改写成健康。关闭原因本身仍标为未证明，不假定是用户关窗、系统休眠或某一特定程序造成。

## 本机接口

- `prepareFaultRescue`：仅在已停止的独占管理员会话中取得元数据票据，不发送模型消息。
- `dispatchPreparedFaultRescue`：管理员浏览器和锁释放后才单次发送；未知结果不重发。
- `reconcileFaultRescueDispatch`：只读恢复固定客户端 UUID 的队列回执。
- `settleFaultRescue`：真实轮次结束证明与服务器业务证据共同结案；`verifiedRecovery: false` 否决模型的恢复声明。
- `faultRescueGate`：即使关闭后备配置，未结束的票据仍禁止启动日常执行器。
- `FaultRescueClient`：仅允许 initialize、精确线程只读、队列及精确轮次中断；不能调用旧站门户工具、创建模型线程或批准交互。

启用配置需显式包含 `faultRescue.enabled`、`scope: "read_only_reconcile"`、既有授权 `threadId`、30–600 秒的 `timeoutSeconds`，可选绝对 `cliPath`。它不重启旧版每分钟 Codex 自动任务。普通浏览器/Node/PowerShell 继续使用隐藏及隔离宿主，不为后备打开用户可见窗口。

运行目录 `fault-rescue.json` 包含本机票据令牌，不纳入 Git、发布包、聊天或通用日志。返回报告只有故障 ID、票据 ID、状态和有限生命周期元数据。`wakeAttempts` 是请求发送次数，不是模型 Token 数；发生后备后真实模型用量由 Codex 统计，不能宣称为零。

## 验证与回退

离线测试使用工厂替身和独立临时目录，覆盖同故障重启去重、发送/结案回执丢失、同时调度、ACK 伪恢复、终态与根轮次关联、共享轮次不中断、五分钟预算、权限拒绝、真实交互证据、退避及启动窗口隔离。它们不发送真实邀请、邮件或模型消息。

发布前还需一次受控的实际队列生命周期验收：确认原聊天收到一次消息、服务端客户端 UUID 正确绑定、模型结束后独占票据可结案；仅探测 queue/list 和 thread/read 不能替代该验收。真实业务恢复由普通执行器官方核对验证，不能把模型文字或 mock 测试当作实际办理成功。

回退触发条件包括构建/回归失败、正常业务退化、重复唤醒、互斥/隔离不成立、无法证明原操作结果或实际模型轮次停止。先停普通执行器并禁用新的后备发送；已有 pending/uncertain 轮次须确认真正结束并处理原票据、租约和日志，再按整版备份恢复源码与构建产物。不要用旧版本忽略新票据后直接启动，也不要抹掉运行证据。回退后验证源码摘要/版本、构建、网页登录与白名单、现有申请/排队/续期数据、官方名单、任务唯一执行和无可见窗口。
